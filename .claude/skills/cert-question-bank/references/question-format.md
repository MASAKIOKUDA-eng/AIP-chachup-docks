# 問題データの形とサンプル

## ファイル

- `data/meta.js` に、次のものをまとめている：
  - 分野（`DOMAINS`）と、回数・1 回の問題数（`SET_COUNT` / `SET_SIZE`）
  - 柱（`PILLARS`）とベストプラクティス（`WA`）
  - ベストプラクティスのページの URL を返す `waUrl(id)`
  - 参照ドキュメント（`DOCS`）
  - 問題の登録関数 `addQuestions`
- `data/set<回>-<a〜d>.js` に問題を書く（a: 第1分野、b: 第2分野、c: 第3分野、d: 第4・5分野）。
- 問題 ID は `<回>-<回の中の通し番号 2 桁>`。番号は、ファイルの読み込み順と、書いた順で決まる。既存の問題の途中に挿入すると、以降の ID と選択肢の並びが変わるので、追加は末尾に行う。

## キー

| キー | 必須 | 内容 |
| --- | --- | --- |
| `d` | ○ | 試験分野（1〜5） |
| `t` | ○ | 試験ガイドのタスク（例：`"1.5 検索メカニズムの設計"`） |
| `topic` | ○ | 何の知識か（例：`"RAG の検索とアクセス制御"`） |
| `wa` | ○ | 判断基準のベストプラクティス ID（`WA` にあるもの） |
| `svc` | ○ | 関連するサービスの配列 |
| `q` | ○ | 問題文。業界・状況・制約を含め、「最も適切な〜はどれですか。」で終える（複数選択は「〜を 2 つ選んでください。」） |
| `c` | ○ | 選択肢。単一選択は 4 つ、複数選択は 5 つ |
| `a` | ○ | 正解の index（0 始まり）。複数選択は配列 |
| `why` | ○ | 選択肢ごとの理由（`c` と同じ順番。正解は「正解。」で始める） |
| `exp` | ○ | 解説。「<ID> は、〜を推奨しています。」で始め、沿う理由を書く |
| `ref` | ○ | `DOCS` のキーの配列 |
| `guide` | | ガイドの見出し ID（リンクを出したいとき） |

## サンプル（単一選択）

```js
addQuestions(6, [
  {
    d: 3, t: "3.3 ガバナンスとコンプライアンス", topic: "大量のデータの引き出しの検知", wa: "GENSEC01-BP04",
    svc: ["AWS CloudTrail", "Amazon CloudWatch", "Amazon Bedrock Knowledge Bases"],
    q: "製薬会社の研究ナレッジベースには、未発表の研究データが含まれる。ある社員の認証情報で、深夜に数千回の検索が短時間に行われていたことが後から分かった。今後、同じような大量のデータの引き出しの兆候にすぐ気づきたい。最も適切な対応はどれですか。",
    c: ["検索の回数には制限を設けず、問題が起きたときに記録をさかのぼって調べることにする",
        "主体ごとの検索や呼び出しの回数を監視し、通常と比べて急に増えたら通知する",
        "ナレッジベースの利用を研究部長だけに限り、ほかの研究者は使えないようにする",
        "深夜の時間帯だけナレッジベースを停止して、深夜の大量の検索ができないようにする"],
    a: 1,
    why: ["後から気づくのでは、データの流出を防げない。",
          "正解。アクセスの記録を監視し、通常と異なる大量の利用をすぐに検知する。",
          "研究の業務に必要な利用まで制限してしまう。",
          "日中の大量の引き出しは防げない。"],
    exp: "GENSEC01-BP04 は、生成 AI サービスと基盤モデルへのアクセスを監視することを推奨しています。主体ごとの呼び出しの回数を監視し、通常と比べて急に増えた場合に通知すると、データの引き出しの兆候に早く気づけます。",
    ref: ["trail", "cwAnomaly"]
  }
]);
```

このサンプルのポイント：

- 4 つの選択肢がほぼ同じ長さ。
- 誤答はどれも「ありそう」だが、それぞれ明確な欠点がある。誤答の欠点は、事後対応、業務の過剰な制限、抜け穴。

## 誤答の作り方のパターン

正解のベストプラクティスに反する方向で、次のような誤答を作る。

- **権限・セキュリティ：** 管理者権限を付ける。アクセスキーを共有する。不要になった権限を残す。パブリックな経路を使う。
- **信頼性：** 単一のリージョンやエンドポイントに依存する。リトライやタイムアウトがない。障害時は手作業で切り替える。
- **コスト：** 常に最大のモデルを使う。プロビジョンドのスループットを常時確保する。長いプロンプトを毎回送る。
- **運用：** 手作業でデプロイする。プロンプトをコードに直書きする。評価やトレースをしない。
- **性能：** 評価用のデータセットなしで変更する。負荷試験をしない。埋め込みの次元を考えずに選ぶ。
- **持続可能性：** 常時起動しておく。必要以上に大きなモデルを使う。不要なデータを保存し続ける。
- **過剰対応：** 業務に必要な利用まで止める。全件を人が確認する。機能自体を廃止する。

1 つの問題で同じパターンの誤答を並べない。異なる理由で誤りになる 3 つを選ぶ。
